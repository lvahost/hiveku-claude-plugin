---
description: Manage this project's custom domains - list, add (with DNS + SSL status), update, remove.
argument-hint: "[e.g. 'add www.example.com to production']"
---

Work on one of the account's Hiveku website projects. Resolve the `project_id` first with `sites_list` (every buildable website_project with its dev/staging/prod URLs, canonical GitHub state and container status) or `project_get({ project_id })` for one, or take it from what the user names. Do NOT use `list_projects` / `get_project` here: those return pm_projects rows, a different id space, and a website UUID 404s against them.
Manage custom domains for THIS project$ARGUMENTS. This project's id is `<the project_id>`.

1. List first: `project_domains_list({ project_id: <the project_id>, tier? })` - each row carries `id`, `domain`, `tier`, `is_primary`, `domain_status`, `ssl_status`, `dns_status`, `dns_records`, `is_apex_domain`. The `id` is what every other tool here takes as `domain_id`.
2. If the domain is an APEX (example.com, no subdomain), call `project_domain_apex_options({ project_id: <the project_id>, domain })` FIRST and lead with what it exists to say: **an apex domain cannot use a CNAME.** That is the single most common reason a custom-domain setup stalls. It returns the static IPs plus provider-specific routes, including Cloudflare CNAME flattening - the cleanest path when you already have Cloudflare access.
3. Add: `project_domains_add({ project_id: <the project_id>, domain, tier: "production"|"staging"|"dev", is_primary? })` - note the tier spelling here is `dev`, not `development`; default is production. The response includes the DNS RECORDS the user must create at their registrar. SURFACE those records verbatim; the user cannot guess them.
4. DNS: `project_domain_dns_records({ project_id: <the project_id>, domain_id?, tier?, check_dns? })` re-reads the required records and, with `check_dns: true`, resolves each one and reports whether it matches. If you have registrar access (Cloudflare, Route53) create the records yourself and verify with `check_dns: true` instead of handing over a list. `project_domain_check_dns({ project_id, tier })` forces a re-check now instead of waiting for the periodic sweep - a negative result minutes after a change usually means "not yet", not "wrong".
5. VERIFY before telling the client it is up: `project_domain_verify({ project_id: <the project_id>, domain_id })`. It checks DNS **and** the SSL certificate, and a domain is only servable once BOTH are good - DNS alone is not enough. On a failed or stuck cert, `project_domain_retry_certificate({ project_id, domain_id, action: "retry_certificate" })`, but a CAA record on the zone that forbids the issuing CA is the usual cause and the retry fails identically until the CAA is fixed.
6. Apex-to-www pair: `project_domain_apex_redirect_set({ project_id, apex_domain, target_domain, redirect_type? })` points example.com at www.example.com (301 by default).
7. MIGRATING AN OLD DOMAIN (olddomain.com → newdomain.com) does not use the apex tool. Attach the old domain with `project_domains_add` WITHOUT `is_primary`, make sure the right one is primary (`project_domains_update({ project_id, domain_id, is_primary: true })`), then run `project_redirects_deploy({ project_id })`. Every non-primary domain 301s to the primary via the CloudFront function. Two caveats that make this a silent no-op if missed: domain redirects are **production tier only**, and **nothing takes effect until that deploy runs**.
8. `project_domains_remove({ project_id: <the project_id>, domain_id })` soft-detaches (is_active=false) - the site stops serving on that host. The user's own DNS records are left alone; re-attach later with the same domain string.
Confirm add/remove; a domain isn't live until its DNS records resolve + SSL provisions (allow 24-48h for propagation). Tell the user to add the returned records, then re-run `project_domain_verify` to watch it flip.
