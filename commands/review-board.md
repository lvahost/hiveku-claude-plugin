---
description: Build + publish the visual review board - a read-only Artifact page of every annotation (screenshot, outline box, comment, status) across both review rails, for a client or PM to look at.
---

Work on one of the account's Hiveku website projects. Resolve the `project_id` first with `sites_list` (every buildable website_project with its dev/staging/prod URLs, canonical GitHub state and container status) or `project_get({ project_id })` for one, or take it from what the user names. Do NOT use `list_projects` / `get_project` here: those return pm_projects rows, a different id space, and a website UUID 404s against them.
Build THIS project's REVIEW BOARD: one self-contained HTML page showing every annotation from BOTH review rails, published as a Claude Artifact (the `Artifact` tool renders an HTML file to a default-private claude.ai link the operator can share with the client or PM). The board is the shared visual STATE of the review queue.

**The board is READ-ONLY.** No buttons, no forms - nothing on it picks, fixes, or resolves anything. Resolution happens in the session via `/hiveku:review` (local rail: flip `status` in `annotations.json`; server rail: fix the code, `pm_tasks_comment`, then `pm_tasks_complete` when the task's feedback is addressed). Since the 2026-08-25 two-way sync links `browser_annotations.task_id` → `pm_tasks.id`, status + comments flow both ways, so completing the task IS the annotation-resolve path - but VERIFY THE SYNC the first time you rely on it on an account: complete, re-fetch `pm_tasks_get`, confirm `resolved_at` actually flipped (legacy annotation rows predate the link and stay open forever). Put the read-only fact on the page itself in one line, so a client doesn't hunt for a resolve button.

STEP 1 - GATHER, both rails. Include RESOLVED annotations too - the board shows the queue's state, not just the work left.
- LOCAL rail (on-disk, gitignored, never leaves the machine): read `.hiveku/review/index.json`; for each row of `pages` (an ARRAY) read `.hiveku/review/<slug>/annotations.json` and note `.hiveku/review/<slug>/screenshot.png`. Per annotation: `{id, type:"rect"|"pin", region (PERCENT coords), comment, priority, annotationType, status:"open"|"resolved", resolvedAt, element:{..., hivekuSource:{file,line,column}}}`.
- SERVER rail (the client's annotations, left in Hiveku): annotations ride ON PM TASKS - no `annotation_*` tools exist. `pm_projects_list`, take the `website` project_type row (that id is a pm_projects id, NOT the website `project_id` above); `pm_tasks_list({ project_id })` for the review tasks; `pm_tasks_get({ id })` on each. Its `data` carries an `annotations` array plus `annotation_count`. Per annotation: `{ id, annotation_type, priority, annotation_text, page_url, page_title, coordinates, screenshot_url, screenshot_key, screenshot_status, capture_method, viewport_size, created_by_name, created_by_email, created_at, resolved_at }`. `screenshot_url` is a directly-fetchable public PNG. An annotation's resolved state IS `resolved_at` - there is no status column: null = open, set = resolved.
- Both rails empty → say so and stop. Point at `/hiveku:review` (capture) or the client's preview review flow; do not publish an empty board.

STEP 2 - FETCH the pixels. The artifact CSP blocks every external host, so the HTML must NEVER reference `screenshot_url` directly - download, then embed.
- Local pages: the PNG already exists at `.hiveku/review/<slug>/screenshot.png`.
- Server annotations: the screenshot is per-ANNOTATION - `mkdir -p .hiveku/review/board-assets` and `curl -s "<screenshot_url>" -o .hiveku/review/board-assets/<annotation id>.png` for each. Then Read one or two of the downloaded PNGs - the Read tool renders images, so you SEE the page and can sanity-check the overlay math in STEP 3 against what the comment describes.
- A screenshot can still be pending: `screenshot_status: "capturing"` with a null `screenshot_url` means the async capture hasn't finished - re-fetch `pm_tasks_get` once shortly, else render that card with a "screenshot pending" placeholder. `"failed"` / `"none"` = no image exists: render the card comment-only and say the screenshot was unavailable. Never leave a broken `<img>`.
- Embed every image as a `data:` URI (`base64 -i <file>`). The rendered page hard cap is 16MB INCLUDING data: URIs - if the sum runs over, downscale (`sips -Z 1400 <file>` on macOS) or re-encode to JPEG first; a review board does not need full-res PNGs. Embed each unique image ONCE: a local page's screenshot is SHARED by all its annotations, so render one figure per page with ALL of that page's boxes overlaid, numbered to match the cards beside it - duplicating a multi-MB data URI per annotation blows the cap for nothing. Server annotations each have their own PNG: one figure per card.

STEP 3 - THE OVERLAY MATH. A figure is `<div style="position:relative">` wrapping the `<img>` at `width:100%; display:block`, boxes `position:absolute` in PERCENT so they scale with the image.
- LOCAL annotations: `region` is already percent coords of the full screenshot - use its fields directly as CSS `left/top/width/height` percentages. `type:"pin"` has no area: render a small fixed-size dot centered on the point instead of an outline.
- SERVER annotations: `coordinates` is VERIFIED against the builder's own renderer (ReviewCanvas.tsx): `{ xPct, yPct, sticky?, viewportY?, viewportWidth? }` - PERCENT FRACTIONS, not CSS pixels, and a POINT (a pin), not a rect. Place the marker at `left: xPct*100%`, `top: yPct*100%` of the rendered screenshot; when `sticky` is true the annotation was pinned to a viewport-fixed element and `viewportY` carries its viewport offset - render those with a 'pinned to viewport' badge at `top: viewportY` scaled by the image width ratio instead. Draw a pin + a ~6% halo circle rather than a box, since there is no width/height. Still log ONE raw annotation first: legacy rows may predate this shape.
- Verify one server box against a PNG you Read in STEP 2: does it land on the element `annotation_text` names? If not, re-derive the math before building twenty wrong cards.

STEP 4 - BUILD `.hiveku/review/board.html` - ALWAYS this exact path (it is the artifact's identity within a session AND the offline fallback; gitignored with the rest of `.hiveku/review/`). Load the `artifact-design` skill before writing, if available. Self-contained: inline CSS, data: URI images, zero external requests, no JS needed. No emojis in the page copy.
- `<title>`: the project's name as a short noun phrase (e.g. `Acme Roofing Review Board`), stable across re-runs.
- Header: project name, generated date, and the one-line read-only notice ("A snapshot for review - fixes and resolutions happen in Claude via /hiveku:review").
- SUMMARY STRIP: one chip per page/task - name plus open vs resolved counts. Local: recompute from the annotations you actually loaded (`status !== "resolved"` = open), don't trust a stale `index.json` row. Server: count `resolved_at` null vs set.
- One SECTION per local page (`slug` + `pageUrl`) and per server task (task title + `page_url` / `page_title`). Each annotation card: its figure (or numbered box on the page's shared figure); beside it the comment (`comment` / `annotation_text`), priority, a status chip (open / resolved - dim resolved cards), created_by when known (`created_by_name` server-side; local rows usually carry none), created/resolved dates, and the located `file:line` when known (`element.hivekuSource` on local rows; server rows have none until `/hiveku:review` locates them - show `page_url` instead).
- Tall full-page figures: cap them (`max-height: 70vh; overflow: auto` on the wrapper) so one long homepage doesn't bury the rest of the board.
- Light+dark safe: define the full light palette as tokens on bare `:root`; redefine under `@media (prefers-color-scheme: dark)` guarded as `:root:not([data-theme="light"])` AND again under `:root[data-theme="dark"]`; give `body` an explicit token background. Anything wide scrolls in its own `overflow-x: auto` container.

STEP 5 - PUBLISH. Call the `Artifact` tool with `file_path: .hiveku/review/board.html`, a stable favicon, and a one-line description. RE-RUNS MUST LAND ON THE SAME URL, and "same file path = same URL" only holds WITHIN one session - a re-run in a NEW session that publishes without `url` MINTS A NEW LINK while the client keeps refreshing the old one. So:
- FIRST publish ever: call `Artifact` with no `url`, then write the returned artifact URL to `.hiveku/review/board-url.txt` (gitignored with the rest of `.hiveku/review/`) so later sessions recover it without guessing.
- EVERY re-run: recover the existing URL BEFORE publishing - read `.hiveku/review/board-url.txt`; if absent, `Artifact` `action: "list"` and match the board's title; if still not found, ask the user for the board link - and pass it as `url` on the publish (then write it to `board-url.txt`). Publishing without `url` creates a SEPARATE artifact, not an update. Publish url-less only once you are sure no board artifact exists yet.
- Never vary the path or filename either: within a session `.hiveku/review/board.html` IS the artifact's identity, and a different path claims a new URL.
Hand the user the URL plus the per-page open/resolved totals in the terminal.
- If the `Artifact` tool is unavailable in this session, the file you wrote IS the deliverable: tell the user to open `.hiveku/review/board.html` in a browser - same HTML either way; it just isn't a shareable link until a session with the tool republishes it.
