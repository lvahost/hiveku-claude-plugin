Social week plan. Context: `account_context_get({ domain: "social" })`.
1. `social_list_accounts` (which platforms can actually post - read `connection_status`, `is_active`, `can_post`, `last_error`; a connected-but-erroring account fails silently at the cron) + `social_analytics_summary` (what worked; note it always returns the trailing 7 days - the route ignores any date args) + `social_pillar_list` (pillars with `target_percentage` and `target_posts_per_week`).
2. Draft the week via `talk_to_department({ domain: "social", message })` - per-platform variants, because one post carries ONE caption to all of its targets (`platform_overrides` is not on the tool and is dropped).
3. Persist as TRUE DRAFTS: one `social_create_post({ content, target_platforms: ["<one slug>"], target_accounts: ["<connected account id>"], pillar_id, title })` per platform slot, and **omit `scheduled_at`**. Setting `scheduled_at` is not a proposal - it writes status 'scheduled' and the every-minute cron publishes it, since the default `approval_status: 'not_required'` passes the cron's filter. `target_accounts` is optional to the tool but mandatory in practice: without it the post 400s at publish time. Slugs are exactly `linkedin`, `twitter`, `facebook`, `instagram`, `tiktok`, `google_business_profile`. Optionally bind each post to its slot with `social_calendar_create({ title, event_type, start_date, target_platforms, linked_post_id })` - `title`, `event_type`, and `start_date` are all required.
4. Present the week and get a yes. Only then add times with `social_update_post({ post_id, scheduled_at })` (future time, account's timezone - a past one is a 400 on create). Do NOT call `social_publish_post` on a scheduled post: on an unapproved post it returns 200 with `pending_approval: true` and moves it OUT of status 'scheduled' into the dashboard approval queue, so it stops shipping until a human approves it.
5. Finish every session of work the same way: persist notable learnings to department memory - read the department's current document with `memory_list({ domain: "<dept>" })`, append your note to the `content` it returns, and send the WHOLE merged document to `memory_update({ memory_id, content })`, which REPLACES it (sending only the new note destroys everything that department had accumulated); use `memory_create({ type: "memory", name: "<dept>", content })` only when no entry exists, and keep `<dept>` to a canonical department name (see hiveku-orient), and reflect the work in Hiveku PM: `pm_projects_list` to find the project (it filters only by `status`; `project_type` is named in its description but is NOT in its schema, so the proxy drops it and you filter the returned list yourself), or `pm_projects_create({ name, project_type })` where project_type is one of seo | ppc | marketing | website | app_dev, then `pm_tasks_create({ project_id, title })` (the field is `title`, not `name`), `pm_tasks_update` as it moves, `pm_tasks_complete({ id, summary })` when the loop is closed. Reopen a task closed too early with `pm_tasks_uncomplete`, never `pm_tasks_update`. Hiveku, not this folder, is the source of truth.
