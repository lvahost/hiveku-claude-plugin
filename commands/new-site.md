---
description: Spin up a NEW website project for this account - from a template, then inject sections.
argument-hint: "[what kind of site - e.g. 'a plumber landing page']"
---
Create a new site project for THIS account$ARGUMENTS. You do the build; the human approves.

1. Pick a starting point: `templates_list({ category?, search? })` (70+ site templates) - read `template_get({ slug })` for the one that fits, or start blank.
2. Create it: `site_create({ name, creation_mode, template_id?, project_type?, domain? })` → returns the new project_id. `creation_mode` is `"blank"` (default) | `"template"` | `"import"`, and **a `template_id` passed without `creation_mode: "template"` is ignored** - you get a bare scaffold and think the template failed. `project_type` is `nextjs` (default) | `vite` | `static-html` | `internal`; there is no `"website"` value. Use `"import"` only for bringing an existing app (it seeds nothing; push the code with `project_import_presign` → PUT tarball → `project_import_finalize`). Creation takes 90-150s. (Clone an existing one instead with `site_clone({ project_id, new_name })` - the clone does NOT carry the database, custom domain, CDN/DNS/cert, or GitHub connection; register an already-hosted site with `site_create_external({ name, external_website_url, external_platform? })`. `external_platform` records where that site lives and takes six values: `"webflow"`, `"wordpress"`, `"squarespace"`, `"wix"`, `"shopify"`, or `"url"` (the default) for a static export or any host not on that list. Pass the platform the site is actually built on: a Shopify, Squarespace or Wix site filed as `"url"` loses the builder's platform fingerprint and the per-platform editing connection that follows it. Pass `"webflow"` for a Webflow site: the tracking snippet still goes in Site settings, Custom code, Footer code, and once the account connects Webflow the project gains the Webflow workspace, the `webflow_*` tools and the webflow chat mode, so CMS content, page SEO, assets, custom code and publishing are editable from Hiveku while pages and styling stay in the Designer. Pass `"wordpress"` for a WordPress site: tracking works today through the snippet and content editing arrives with the Hiveku WordPress plugin. Squarespace, Wix and Shopify sites track through the same snippet today, and editing arrives with each platform's own connection; a Shopify STORE (products, orders, inventory) is the separate commerce integration and is unaffected by this value. The value cannot be changed by `site_create_external` later; a wrong platform is corrected in the project's settings.)
3. Add sections: `components_list({ category?, intent?, style?, search? })` (~220 prebuilt sections; filters compose with AND, and an unfiltered response paginates 100 at a time - use `facets.categories` from the response to narrow) → `components_add({ project_id: <new id>, components: [...], dry_run: true })` first, read `files_to_write` + `skipped`, then run it for real. It injects each section's files plus the full dependency closure (helper components, client islands, missing npm deps in package.json); it does NOT attach a section to a page - you wire it in yourself in code. Caps: 16 components / 40 explicit `files` per call; 400 `unsupported_project_type` on anything that is not a Next.js / internal project.
4. **Wire the forms, or the client's leads go nowhere.** A new site's forms are inert until something is bound to them. `workflow_bulk_provision_for_project({ project_id, overrides: { RECIPIENT_EMAIL, SOURCE_LABEL }, dry_run: true })` scans the project for form components and, per form, instantiates the canonical template, provisions the webhook, and sets that form's `NEXT_PUBLIC_*_WEBHOOK_URL` project secret. One call for the whole site. Read `skipped` and `errored` in the dry run (a skipped form is a form nobody hears from), then re-run without `dry_run`. `overrides` apply to EVERY form, so if forms need different recipients, do those with `workflow_create_from_template` + `workflow_bind_form` individually, or fix after with `workflow_set_recipient`. Then `workflow_test` each workflow and read its `would_have` payload before telling the client it is live. See the `hiveku-automation-agency` skill.
5. Download it locally to keep building: pull it local and continue with `/hiveku:code` (which verifies and deploys).
6. Point a domain at it with `/hiveku:domains` and configure the CMS with `/hiveku:cms`. Ship it with `/hiveku:deploy` (tier `development` first - nothing is client-visible until a `production` deploy, and the tiers do not share code).
Confirm before `site_create`/`site_delete` (delete is irreversible + drops any Supabase billing). Reflect the new project as a PM task if this is client work.
