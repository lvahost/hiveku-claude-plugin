description: "Answer Google reviews (\"someone left us a bad review\") - weekly Google Business Profile (GBP) review sweep: triage, draft replies, human approval, one confirmed reply at a time."
---
Google review sweep. Load `references/local-seo.md` from the **hiveku-seo-agency** skill (Play L4) before running this. SLA: 24h on 1-2 star, 72h otherwise.
1. Context: `account_context_get({ domain: "seo" })` - brand voice, escalation contact, and any rule about who speaks publicly. Then `seo_connections_list` for the GBP `connection_id`s.
2. Triage read (free, DB-only): `seo_gbp_reviews({ connection_id, min_rating: 1, max_rating: 3, limit: 50 })` for what needs a human today, then `seo_gbp_reviews({ connection_id, limit: 100 })` for the rest. Sort by `review_time` descending, then rating ascending. Unanswered means `reply` is null or empty; where `reply` is already set an owner answered, so ask before overwriting them.
3. Triage each: 5-star with text (short warm reply naming the service), 5-star bare (very short, still reply), 3-4 star (thank, name the gap, offer an offline channel), 1-2 star (negative protocol below).
4. Draft the whole set in ONE `talk_to_department({ domain: "seo", message })` call with the brand voice attached, then edit every reply by hand. Batch drafting is efficient; batch publishing is not allowed.
5. Show the client the full draft set. **Per-reply approval for every 1 and 2 star.** Negative protocol: never argue, never confirm the reviewer's specifics where that implies a private relationship (a compliance breach in regulated verticals, not a style choice), never offer compensation publicly, never dispute facts in public. Acknowledge, state the standard the business holds itself to, name a human and a direct channel. Under 60 words. The audience is the next prospect, not the reviewer.
6. Publish ONE review at a time: `seo_gbp_review_reply({ connection_id, review_id, reply })`. The first call without `confirm` publishes nothing - it returns a preview (the reply text and length, the review, the connection) with `requires_confirm: true`. Read the preview (it catches a wrong `connection_id`, which on a multi-location account means replying on the wrong branch), then repeat the IDENTICAL call with `confirm: true`. Max 4096 chars, and it REPLACES any existing owner reply. **Never loop this tool** - a batch published in seconds reads as automated to every human who sees it.
7. `seo_gbp_review_reply_delete({ connection_id, review_id })` has one legitimate use: an owner reply that is factually wrong, off-brand, or exposes private information. Same two-step confirm; deletion is visible and effectively permanent, so it needs client sign-off exactly as publishing does.
8. GBP POSTS are not this command and have no tool here - publish them via `social_create_post` with platform `google_business_profile` (approval queue). Never claim to have posted from here.
9. Report: replied count, escalated count, reply coverage as a percentage with the misses named, and any 1-2 star still open past 24h.
10. Finish every session of work the same way: persist notable learnings to department memory - read the department's current document with `memory_list({ domain: "<dept>" })`, append your note to the `content` it returns, and send the WHOLE merged document to `memory_update({ memory_id, content })`, which REPLACES it (sending only the new note destroys everything that department had accumulated); use `memory_create({ type: "memory", name: "<dept>", content })` only when no entry exists, and keep `<dept>` to a canonical department name (see hiveku-orient), and reflect the work in Hiveku PM: `pm_projects_list` to find the project (it filters only by `status`; `project_type` is named in its description but is NOT in its schema, so the proxy drops it and you filter the returned list yourself), or `pm_projects_create({ name, project_type })` where project_type is one of seo | ppc | marketing | website | app_dev, then `pm_tasks_create({ project_id, title })` (the field is `title`, not `name`), `pm_tasks_update` as it moves, `pm_tasks_complete({ id, summary })` when the loop is closed. Reopen a task closed too early with `pm_tasks_uncomplete`, never `pm_tasks_update`. A memory_update that destroyed content is recoverable: `memory_list_versions({ memory_id })` lists the snapshots taken before every PUT or DELETE, and `memory_restore_version({ version_id })` restores one (it works for deleted entries too). Hiveku, not this folder, is the source of truth.
